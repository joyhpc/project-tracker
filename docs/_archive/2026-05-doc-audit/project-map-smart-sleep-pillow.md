# Smart Sleep Pillow 项目地图示例

这份文档用 `https://github.com/joyhpc/smart-sleep-pillow` 对应的 `PILLOW` 项目作为样例，说明现在的项目地图应该如何使用，以及它解决了什么可用性问题。

## 为什么用这个例子

仓库里已经有对应项目样例：`projects/PILLOW.yaml`。

这个样例非常适合验证项目地图，因为它同时具备：

- 已完成的概念阶段
- 正在推进中的设计阶段
- 可并行推进的任务
- 需要等待依赖的后续任务
- 已知阻塞点
- 明确的关键路径
- 决策与文档沉淀

也就是说，它不是一个“空项目”，而是一个能够真实反映地图价值的中途项目。

## 推荐使用方式

### 1. 终端地图（默认入口）

```bash
PYTHONPATH=. ./pt switch PILLOW
PYTHONPATH=. ./pt map
```

终端地图会直接回答 5 个问题：

1. 我现在在哪
2. 当前最该推进什么
3. 还有哪些任务可并行推进
4. 哪些任务在等依赖 / 被阻塞
5. 关键路径长什么样

### 2. HTML 地图（汇报 / 截图 / 交接）

```bash
PYTHONPATH=. ./pt map --html --output /tmp/project-map-pillow
```

会生成：

- `/tmp/project-map-pillow/pillow-project-map.html`
- `/tmp/project-map-pillow/pillow-project-map.png`（若本机 playwright/chrome 可用）

### 3. 保留原可视化命令

```bash
PYTHONPATH=. ./pt visual --output /tmp/project-map-pillow
```

`pt visual` 现在与 `pt map --html` 使用同一套地图渲染逻辑，避免终端地图和 HTML 地图表达不一致。

## 这次地图优化解决了什么问题

旧版地图的主要问题是：

- 把并行 DAG 强行画成线性流水线，容易误导
- ready / waiting 顺序可能漂移，不利于稳定阅读
- 只看颜色，不告诉你“在等谁”或“为什么阻塞”
- HTML 地图和终端理解模型不统一
- 地图入口不明显，用户不容易知道该用哪个命令

这次之后，地图被明确分成两种形态：

- `pt map`：终端一眼看清当前状态
- `pt map --html` / `pt visual`：用于截图、汇报、交接

两者共享同一份项目地图快照。

## 读图方法

### 顶部摘要

顶部先给你：

- 总进度
- 总工期
- 关键路径长度
- 可推进任务数
- 阻塞任务数
- 文档覆盖情况
- 生效决策数
- 仓库绑定状态

如果 `repo` 路径已经失效，地图会直接提示“仓库路径缺失”，而不是静默失败。

### 当前焦点

`当前焦点` 的选取规则是：

1. 优先进行中的任务
2. 若没有进行中任务，则选择 ready 里最值得先做的任务
3. ready 任务优先考虑关键路径，再看 slack，再看拓扑顺序

这比“随便挑第一个 ready”更稳定，也更贴近真实项目管理。

### 阶段泳道

每个阶段不再画成假装串行的箭头链，而是分成：

- 进行中
- 可推进
- 阻塞
- 等待依赖
- 已完成

这样看 `PILLOW` 项目时，你会直观看到：

- `硬件设计` 正在进行中
- `固件设计` / `结构设计` 可并行推进
- `硬件评审` 还在等待 `硬件设计`
- `板级调试` 有明确阻塞原因

这就是“项目地图”比“任务列表”更有用的地方。

## 对交接的价值

如果把这张地图发给另一个 agent / 同事，对方不需要先看完整 YAML，就能快速知道：

- 当前主线在哪
- 并行支线有哪些
- 风险集中在哪
- 项目是否具备文档与决策沉淀
- 下一步最应该从哪里接手

这正是项目地图应该承担的职责。
