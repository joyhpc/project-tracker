# Prompt 架构升级 — 超级 LLM 回复 + Nova 批判分析

## 核心方案：v4 架构 — AST 语义切块 + 本地 BM25 检索

### 四个问题的解答

| 问题 | v3（当前） | v4（提议） |
|------|-----------|-----------|
| 知识表示 | 信号词匹配提取句子 | Markdown AST 按标题切块，保留原始结构 |
| 上下文选择 | 全部堆进去（最多 8 条） | BM25 检索 Top-3 相关块 |
| 结构化保留 | 丢失（表格被打散） | 原样穿透（XML 封箱） |
| 可扩展性 | 信号词列表需维护 | IDF 自动适应任何领域 |

### 技术栈

- Markdown AST 解析：按 `#` 标题层级切分为 KnowledgeChunk
- 分词：英文/数字连字提取 + 中文 Bigram 滑动窗口（零依赖）
- 检索：BM25（ElasticSearch 底层算法），纯数学，确定性
- 查询扩展：当前任务名 + note + 用户问题 → 联合查询
- 封装：XML 标签保留结构，LLM 能识别来源和原生表格

### 数据流

```
pt done → note_file (自由 markdown)
                ↓
pt prompt → parse_markdown_to_chunks() → KnowledgeChunk[]
                ↓
         → LocalBM25Engine.search(expanded_query, top_k=3)
                ↓
         → XML 封箱 → 组装 prompt
```

## Nova 批判分析

### ✅ 认同

1. **AST 切块是正确方向**。按标题切分比按句提取好太多 — 保留了上下文完整性和结构化数据。用户写 markdown 时自然会用标题分段，这个假设合理。
2. **BM25 替代信号词是核心突破**。IDF 机制天然给专业术语高权重，给废话低权重，不需要维护任何词典。这解决了我最头疼的问题。
3. **中文 Bigram 分词方案务实**。不依赖 jieba 等第三方库，Bigram 对专业术语的覆盖率足够（"降维"、"打击"、"声场"、"偶极"都能命中）。
4. **XML 封箱保留结构**。表格、对比矩阵原样送入 LLM，比提取句子强 10 倍。

### ⚠️ 需要调整

1. **角色和任务指令不能丢**。v4 方案只解决了上下文选择问题，但 v3 的问题类型检测 + 角色设定 + 任务指令模板仍然有价值。应该是 v3 框架 + v4 上下文引擎的混合。
2. **top_k=3 可能不够**。如果一个问题涉及多个已完成任务（比如"综合市场调研和概念设计的结论，评估可行性"），3 个块可能覆盖不全。建议 top_k 可配置，默认 5。
3. **查询扩展需要加入依赖链**。当前只用"任务名 + note + 问题"做查询，但应该加入当前任务的直接依赖任务名，因为依赖链上的知识天然最相关。
4. **空标题文档的处理**。如果用户的 note_file 没有任何标题（纯文本），整个文件会变成一个巨大的 chunk，BM25 匹配会失效。需要 fallback：无标题时按段落（空行）切分。
5. **性能不是问题但缓存有价值**。BM25 索引构建是 O(n) 的，几十个文件毫秒级。但如果频繁调用 `pt prompt`，可以缓存索引到 `.pt/bm25_cache.json`，只在文件变更时重建。

### 🎯 实施计划

v4 不需要一步到位，可以分两步：

**Step 1（立即可做）**：实现 AST 切块 + BM25 检索，替换现有的信号词提取。保留 v3 的角色/指令框架。
- 新增 `tracker/knowledge.py`：KnowledgeChunk + tokenize + parse_markdown_to_chunks + LocalBM25Engine
- 修改 `tracker/prompt.py`：`_build_product_background()` 改用 BM25 检索替代信号词匹配

**Step 2（后续优化）**：
- 查询扩展加入依赖链
- 缓存机制
- `pt done --summary` 可选的结构化摘要（不强制）
