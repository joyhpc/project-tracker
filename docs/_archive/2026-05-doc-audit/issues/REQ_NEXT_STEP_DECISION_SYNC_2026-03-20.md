# ❓ 核心技术探讨与决策同步

## 🤔 问题 1：`pt req` 应该如何识别“同一类文档角色”，而不是被文件名牵着走？

**背景说明：**  
当前 `project-tracker` 已经落地了第一版 `pt req init / index / check`，并且为了兼容 A57 这类已有项目，代码里加入了“按文档角色模式识别现有文件”的逻辑，而不是简单按固定文件名生成。这部分主要影响 `tracker/requirements.py` 和 `tracker/templates/requirements/.../manifest.yaml`。  

**核心疑问：**  
对于“第一性原理需求”“项目起始三问”“需求追溯矩阵”“当前有效结论”“应用目标矩阵”这些文档角色，未来我们到底要采用哪一种长期规则作为正式标准？  
是：
1. 强制统一文件名和目录结构；
2. 允许项目自由命名，但由 `manifest patterns` 去识别角色；
3. 定义“文档角色 ID + 可变文件名”的双层机制，由索引或元数据声明某个文件扮演什么角色。  

**如果不解决的潜在风险：**  
如果这件事不先定，`pt req` 后面越做越深时就会碰到根本性歧义：同一项目可能被重复生成一套“看起来相同”的文档，或者旧项目因为命名不同被误判为缺失；更严重的是，不同项目会逐渐长出不同的“隐式规则”，最后工具无法稳定复用，只能回到人工判断。

**✍️ 人类回复区 (Human Reply Here)：**  
这是一个非常经典且切中了工具链架构设计核心的问题。在构建开发者工具（CLI, 内部平台）或文档即代码（Docs-as-Code）系统时，**如何处理“逻辑角色（Role）”与“物理存储（Filepath）”的解耦**，是决定工具未来能否存活和推广的关键分水岭。

你的担忧极其准确：如果不尽早确立第一性原理，`project-tracker`（简称 `pt`）最后必然会陷入“正则地狱”和永无止境的向下兼容技术债中。

直接给出结论：**强烈建议采用【方案 3】（定义“文档角色 ID + 显式绑定配置”的双层机制）作为长期正式标准。**

同时，方案 1 和方案 2 现有的代码不需要抛弃，而是应该**改变它们的执行时机，将其降级并限制在 `init` 阶段作为辅助手段。**

以下是深度的架构推演和落地方案：

---

### 一、 为什么方案 1 和方案 2 绝不能作为长期标准？

我们可以把 `pt` 看作一个数据库，文档角色是 Schema，文件是 Data。

1. **方案 1（强制统一文件名）的死穴：落地阻力极大。**
   它只适合从零开始的全新项目。对于 A57 这样的历史包袱项目，或者未来有不同语言偏好的团队，强迫改名会破坏原有的 Git 历史和团队习惯。如果工具过于“独裁”，最终业务团队会放弃使用工具。
2. **方案 2（Pattern 模式识别）的死穴：脆弱且充满歧义。**
   在系统设计中，这是典型的**“启发式猜测（Heuristic）”**，把它作为日常运行时的标准是灾难性的：
   * **多重匹配陷阱（歧义）**：如果目录里同时存在 `01-应用目标矩阵.md` 和 `旧版-应用目标矩阵(废弃).md`，模式识别该信哪个？
   * **状态幽灵（误判）**：用户某天把文件改名为 `项目核心目标.md`，超出了你的正则范围。`pt req check` 立刻误判为缺失，并在下次运行时重复生成一份空文档。
   * **隐式规则蔓延**：随着接入 B88、C99 等不同项目，你的 `requirements.py` 会塞满针对各个项目的 regex 和 `if-else`，最后代码逻辑将不可维护。

---

### 二、 长期架构设计：方案 3 的双层解耦机制

**“显式优于隐式” (Explicit is better than implicit)** 是基础设施级 CLI 工具（如 Terraform, Helm 等）的铁律。`pt` 工具内部应该**只认 ID，不认文件名**。

#### 1. 定义不可变的「角色 ID」（Logical Role ID）
在 `tracker/requirements.py` 中，将文档角色抽象为全局唯一、不可变的常量/枚举：
* `req_first_principles` (第一性原理)
* `req_startup_q3` (项目起始三问)
* `req_trace_matrix` (需求追溯矩阵)
* `req_target_matrix` (应用目标矩阵)

#### 2. 引入项目级「显式绑定机制」（Single Source of Truth）
工具需要一个确定的地方来查询 `Role ID -> Filepath` 的映射。推荐结合使用以下两种载体：

* **载体 A：项目级索引文件（必须）**
  在被追踪的项目根目录（如 `.pt/tracker-state.yaml` 或直接复用已有的项目配置），生成一个绑定清单。**这是 `pt req check` 唯一信任的数据源。**
  ```yaml
  roles:
    req_first_principles: "docs/1-First-Principles(A57).md"
    req_startup_q3: "docs/产品立项三问.md"
  ```
* **载体 B：文档内元数据 Frontmatter（强烈建议作为辅助）**
  允许文件叫任何名字，但在 Markdown 顶部使用 YAML 声明身份。这是极强的防丢机制，用户在 IDE 里随意移动文件也不怕。
  ```markdown
  ---
  pt_role: req_trace_matrix
  ---
  # 需求追溯矩阵
  ```

---

### 三、 现有的代码如何重构？（变废为宝）

在这个双层机制下，你目前写在 `tracker/templates/requirements/.../manifest.yaml` 里的 Pattern 识别逻辑**不要删，而是要改变它的执行时机**。

未来的工作流应被严格切分为两个阶段：

#### 阶段 A：发现与绑定（只在 `pt req init` 时发生）
这是方案 1 和 2 发挥价值的地方：
1. **全新项目**：执行 `pt req init`，此时没有历史文件。触发**方案 1**，按标准模板生成规范文件，并**自动将路径写入 YAML 索引中**。
2. **A57 等老项目首次接入**：执行 `pt req init`。触发**方案 2**，工具使用 Pattern 去扫描全盘。
   * **核心动作**：如果正则猜中了某个文件，**把这个文件“转正”**，即：立刻将它的路径硬编码写入该项目的 YAML 索引中（或给它强行加上 Frontmatter）。
   * *设计思想：Pattern 仅仅是一个“一次性的自动发现工具”，猜完一次并固化到配置后，它的历史使命就彻底结束了。*

#### 阶段 B：日常校验与追踪（`pt req check / index`，长期态）
**这个阶段必须彻底禁用 Pattern 猜测！**
`pt req check` 的代码将变得极其简单、极度稳定：
1. 工具读取项目里的 `.pt/tracker-state.yaml`。
2. 查找字典：`filepath = config.get("req_first_principles")`
3. 如果拿到了路径，就只去检查这个精确的文件在不在。
   * 如果文件不在，报明确的错误：“配置中声明第一性原理路径为 xxx，但文件丢失”。
   * 如果配置里根本没有这个角色，报：“未绑定第一性原理文档，请生成”。

---

### 四、 针对你的担忧，重构后的收益总结

采用方案 3 并重构工作流后：

* **同一项目被重复生成多套文档？**
  **彻底解决**。`pt req init / generate` 在生成前只查 YAML 索引。只要 `req_first_principles` 这个 key 有值（无论它对应的文件名多奇葩），工具都会拦截生成动作，杜绝重复。
* **旧项目因命名不同被误判缺失？**
  **彻底解决**。只要在第一次接入时用 Pattern 扫描把旧名字写入了配置，以后 `check` 就顺着设定的路径去检查。
* **不同项目长出不同的隐式规则，工具无法复用？**
  **彻底根除**。`tracker/requirements.py` 里不再需要写任何 `if "A57" in project` 或复杂的正则适配代码。复杂的映射关系被**下放并显式化**到了各个项目自己的配置文件中。工具的核心 Python 代码实现了 100% 的稳健复用。

**下一步 Action Items 建议：**
1. 在现有的项目状态模型中加入 `Role Bindings` 字典。
2. 把 `check` 和 `index` 流程里按正则遍历文件的逻辑删掉，改为直接读字典。
3. 把按正则匹配文件名的逻辑封装成 `auto_discover()` 函数，仅挂载到 `init` 流程下。

## 🤔 问题 2：需求 ID、版本冻结和“当前有效结论”到底以什么机制成为单板真理源？

**背景说明：**  
当前 `pt req` 已经能生成骨架和检查基本缺页，但还没有真正定义“需求变更后如何保持追溯链不失真”。尤其在 A57 这种硬件项目里，需求会经历多轮澄清、冻结、松动、重新冻结，像 3.5Gbps/Lane 这种约束只是其中一个例子，后续还会有接口、能力边界、验证口径、EEPROM 字段、放行判定等持续变化。  

**核心疑问：**  
我们是否要正式定义一套统一机制，回答下面这几个问题：  
1. 每条需求是否必须有稳定的 `需求ID`，且一旦创建后永不复用；  
2. 需求变更时，是“原 ID 更新版本”，还是“旧 ID 失效 + 新 ID 生效”；  
3. “当前有效结论”文档究竟是摘要页、冻结页，还是唯一裁决页；  
4. `pt req check / trace` 后续是按“最新文档优先”判断，还是按“显式生效状态”判断。  

**如果不解决的潜在风险：**  
如果没有统一的版本与生效机制，需求追溯矩阵最终会沦为静态表格，而不是可裁决的系统。届时文档会很多，但团队无法回答“此刻到底哪个口径生效”；`pt` 也无法自动判断某个验证结果是在验证旧需求还是新需求，工具层会失去决策价值。

**✍️ 人类回复区 (Human Reply Here)：**  
这是一个极其敏锐且直击硬件系统工程（Systems Engineering）命门的问题。

在 A57 这种复杂度高、单板打板/流片试错成本极大的硬件项目中，如果你不正式定义这套“版本与生效机制”，`pt req`（需求工具）最终必然会沦为一个**“高级的 Markdown 格式刷”**，而你们的需求追溯矩阵（RTM）也会变成一张**“无法自证清白、无人敢信的静态死表”**。

要让需求真正成为“单板真理源（Single Source of Truth, SSOT）”并让工具具备裁决能力，必须引入**配置管理（Configuration Management）和状态机（State Machine）**的底层逻辑。结合现代硬件工程（如车规 ISO 26262、航空 DO-254）的最佳实践，以下是对你四个核心疑问的正式定调和机制设计：

---

### 一、 核心疑问的解答与“四大基本法”

#### 1. 每条需求是否必须有稳定的需求 ID，且永不复用？
**结论：绝对必须。ID 是全局唯一的“物理主键（Primary Key）”，一旦创建，终生锁定，【绝对不可复用】。**
*   **工程逻辑**：需求 ID（如 `A57-HW-0125`）是被下游无数实体强依赖的锚点——验证代码里的宏、自动化测试脚本、EEPROM 的寄存器映射表、原理图上的 Net Label。
*   **复用的灾难（为何要引入“墓碑机制”）**：如果 `0125` 曾经代表“支持 3.5Gbps”，后来该需求被砍，三个月后你把 `0125` 重新分配给“支持 I2C 写保护”。此时回头看历史 EVT 测试报告上写的“Pass: 0125”，就会产生极其恐怖的语义错乱。
*   **机制**：废弃的需求只能变更为 `Obsoleted` 状态，作为“墓碑”留在系统底表中，永远占坑，新需求必须申请单调递增的新 ID。

#### 2. 需求变更时，是“原 ID 更新版本”，还是“旧 ID 失效 + 新 ID 生效”？
**结论：视变更的“破坏性”而定，推荐采用“参数微调升版本，架构颠覆换 ID”的混合机制。**
在工具底层，追溯的最小维度不应是 `ID`，而必须是 **`ID + Version`**。

*   **场景 A：参数演进 / 边界松动（原 ID 升版本）**
    *   *示例*：如你所说，SerDes 速率从 `3.5Gbps/Lane` 放宽为 `3.2Gbps`，或者 EEPROM 增加了一个放行判定字段。
    *   *机制*：ID 保持不变，版本从 `v1.0` 升级为 `v1.1`。
    *   *逻辑*：因为下游的**验证对象和验证方法没有变**，测试工程师只需要去修改测试脚本里的 Pass/Fail 阈值即可。
*   **场景 B：技术路线推翻 / 意图重构（旧 ID 废弃 + 新建 ID）**
    *   *示例*：原定“通过 I2C 读取温度”，后推翻改为“走 PCIe In-band 监控”。
    *   *机制*：旧 ID 设为 `Obsoleted`，新建全新 ID。因为这种变更意味着原有的原理图设计、测试环境、甚至责任人都彻底翻篇了，必须物理切断旧的追溯链。

#### 3. “当前有效结论”文档究竟是摘要页、冻结页，还是唯一裁决页？
**结论：它必须是工程运行的“唯一法典（Sole Arbitrator）”。但在形态上，它绝不能是一份人工维护的 Word/Wiki，而必须是由 `pt req` 动态生成的“只读基线快照（Baseline Snapshot）”。**
*   **破除“双重真理源”**：硬件工程最怕的现象是——邮件里架构师同意改了，会议纪要写了规格松动，微信群里 PD 拍板了，**但底层需求代码没改**。最后测试按旧文档测报 Fail，研发拿聊天记录说 Pass，互相扯皮。
*   **机制铁律**：会议纪要、Jira Ticket 都是“变更的动因（Rationale）”；而 `pt req` 里的数据才是“当前的法律”。只要妥协结论没有落实为需求代码并被工具接纳，在工程验证和放行判定时一律视为**非法/无效**。出了偏差，只认 `pt req` 输出的基线。

#### 4. `pt req check / trace` 后续是按“最新文档优先”，还是按“显式生效状态”判断？
**结论：坚决抛弃“按最新时间戳”判断，必须严格按照“显式状态（Explicit Status） + 基线（Baseline）”判断。**
*   **“最新”的致命陷阱**：工程师可能正在某个分支上草拟下一代 DVT 阶段放宽的参数，此时文件的时间戳是“最新的”，且还在讨论中。如果工具自动抓取它作为真理，就会用未定稿的草案去拦截当前 EVT 产线的放行。
*   **机制**：`pt req` 只认显式的元数据标签。处于 `Draft` 或 `Reviewing` 状态的需求，对 `trace` 和验证工具链是**完全隐形**的，只有 `Active` / `Frozen` 状态才参与计算。

---

### 💡 落地建议：如何让 `pt req` 进化为“单板仲裁者”？

为了不让追溯矩阵沦为静态表格，你的 `pt req` 工具链需要在下一版本中引入**配置管理（CM）**的三层能力：

#### 第一层：强制实施元数据契约（Metadata Contract）
建议在需求文件（如 Markdown 或 YAML）头部强制要求规范的数据结构，`pt req` 解析并依赖这些字段：
```yaml
id: A57-HW-REQ-0042        # 全局唯一，永不复用
version: 1.2               # 参数变更必须升版本号
status: Active             # 状态机：Draft | Reviewing | Active | Obsoleted
baseline: A57_EVT_Release  # 绑定的里程碑基线
supersedes: ~              # 如果是重构换了新ID，这里记录废弃的旧ID以备溯源
rationale: "Issue #405: 测试发现3.5G裕量不足，经03-20 CCB批准降为3.2G"
```

#### 第二层：阻断与基线冻结机制 (`pt req check / freeze`)
1. **防脑裂 (`check`)**：工具扫描时，如果发现同一个 ID 存在两个同为 `Active` 的版本，直接抛出 `Fatal Error` 熔断执行，强迫研发介入解决冲突。
2. **打基线 (`freeze`)**：在 EVT/DVT 投板前夜，执行类似 `pt req freeze --tag A57-EVT-v1` 的命令。工具将当前全库所有 `Active` 的需求锁死，生成一份带 Hash 签名的只读 JSON/PDF。**后续打板、发包、吵架，完全以此基线快照为准。**

#### 第三层：追溯防失真与漂移侦测 (`pt req trace`)
这是解决你“到底哪个口径生效”终极痛点的核心：

*   **测试用例强绑定版本**：验证团队的报告或测试脚本不能只写 `Verifies: REQ-0042`，必须写 `Verifies: REQ-0042 v1.1`。
*   **侦测需求漂移（Requirement Drift）**：当硬件侧将速率改为 3.2Gbps 并把需求升为 `v1.2` 且 `Active` 时。执行 `pt req trace` 不会简单地打个绿色的勾，而是立刻标黄告警：
   > ⚠️ **Verification Stale (版本失步)**:
   > 测试报告 #899 验证的是 `A57-HW-REQ-0042 (v1.1)`，但当前真理源生效需求已升级为 `v1.2`。请验证团队确认 3.5G -> 3.2G 的变更，并提交新结果。

**总结：**
不要害怕在初期引入这些看似繁琐的规则。在复杂的硬件工程里，**“宁可流程僵化，绝不容忍模棱两可”**。通过在工具底层硬编码**“不可变 ID、显式版本号、受控状态机、基线快照”**，`pt req` 就能真正从一个“文本解析脚本”，蜕变成为驱动 A57 硬件项目的最高法官。

## 🤔 问题 3：需求体系最终要不要强制闭环到 `pt` 的任务、验证和放行门禁里？

**背景说明：**  
现在 `project-tracker` 已经有 DAG/CPM、`docs`、`review`、`gate`、`prompt`，而 `pt req` 目前只做到“生成、索引、检查”。这意味着需求文档系统和项目执行系统目前仍是“弱连接”的。后续如果继续做 `req trace` 和 `req attach`，就必须决定需求是否只是“参考资料”，还是要真正驱动任务和放行。  

**核心疑问：**  
对于一条正式需求，我们最终是否要把它强制闭环到下面这条链里：  
`需求ID -> 目标文档 -> 接口/实现 -> 验证记录 -> 当前有效结论 -> gate / release 判定`  
换句话说，后续 `pt` 是否应该支持以下强约束：  
1. 某些关键需求没有对应验证文档时，不允许进入放行判定；  
2. 某些关键需求没有当前有效结论时，`pt gate` 直接给出 caution / no-go；  
3. `pt trace` 不是“文档索引器”，而是“需求闭环检查器”。  

**如果不解决的潜在风险：**

### 一、 对三个“强约束”的定调与升级建议

这三个约束在系统工程（如车规级 ASPICE、航空 DO-178C 等高可靠性软件开发）中被称为**需求双向追溯（Bidirectional Traceability）**。为了在 `pt` 中落地，我们需要做如下设计：

#### 1. “某些关键需求没有对应验证文档时，不允许进入放行判定”
*   **定调：绝对必要。这把控的是“验证覆盖率（Coverage）”。**
*   **落地修正（引入分级制）：** 绝对不能“一刀切”，否则研发会为了应付流程去写一堆无意义的空文档。`pt req` 的元数据（Frontmatter）必须引入 `Level` 或 `Severity` 属性。
    *   **核心需求（如 P0/P1、安全合规、主链路）：** 实施**硬阻断（Hard Blocker）**。找不到关联的 `pt docs/tests`，门禁直接决绝。
    *   **边缘需求（如 P2/P3、UI 微调）：** 实施**软提示（Soft Warning）**。允许缺失验证文档，仅在 Gate 报告中列入风险清单。

#### 2. “某些关键需求没有当前有效结论时，pt gate 直接给出 caution / no-go”
*   **定调：绝对必要。仅仅有“文档链接”是不够的，必须穿透到“结论状态（Status）”。**
*   **落地修正（结构化结论）：** 这要求 `pt` 的下游环节（评审文档、测试报告）不能只是纯文本。它们必须透出机器可读的状态（例如 `result: PASSED | FAILED | BLOCKED | OUTDATED`）。
    *   `pt gate` 的判定逻辑不再是人工确认，而是执行一个自动化断言：`IF ANY(Critical_Req.Result != PASSED) THEN return NO-GO`。这就是用证据链做决策。

#### 3. “pt trace 不是文档索引器，而是需求闭环检查器”
*   **定调：这是最核心的认知升级，也是 `pt trace` 的灵魂。**
*   **落地修正（计算引擎化）：** `pt trace` 应该从一个 `grep` 式的“查询工具”，进化为**合规断言引擎（Compliance Engine）**。它在后台计算出“需求追溯矩阵（RTM）”，并主动高亮两类致命异常：
    *   **正向断链（漏做/漏测）：** 有 Req，但往下追溯不到 Task 或验证结论。
    *   **逆向断链（镀金/夹带私货）：** 有一大堆 Task 或代码，但往上追溯不到任何 Req ID。

### 二、 架构挑战：如何让“强约束”不变成“繁文缛节”？

实施强约束最大的风险，是引发研发团队的反感：“为了发个版，我得在各个系统里填几十个关联表单”。为了让 `pt` 既有硬核的约束力，又有极佳的开发者体验（DX），建议引入以下三种“柔性”设计：

#### 1. 策略即代码 (Policy-as-Code)
强约束的力度应由项目当前的阶段决定。不要把拦截规则写死在 `pt` 的源码里，而是在项目的根目录（如 `.pt-workspace.yaml`）中开放配置：
```yaml
gate_policies:
  traceability:
    require_verification: true
    blocking_levels: ["P0", "P1"]    # 只有高优需求未闭环才会阻断发布
    allow_implicit_approval: false   # 是否允许无测试报告，仅凭 Code Review 放行
```
这样，早期敏捷团队可以配得宽松（只看 Warning），而发版前的交付阶段可以切到极度严格的模式。

#### 2. 自动化关联（无感挂载 / Shift-Left）
绝对不要让开发者手动去维护 Markdown 里的映射关系。`pt` 应该做到“顺手即闭环”：
*   **开发侧：** Commit Message 或 PR 描述里带上 `#REQ-123`。
*   **测试侧：** 自动化测试脚本（如 Pytest）的用例名带上 `test_req_123`。
*   `pt trace` 运行时，自动用正则把这些离散的“脚印”抓取并拼装起来，建立图谱的连线。只要开发者按规范干活，闭环是自动生成的。

#### 3. 必须提供“逃生舱”（Waiver 豁免机制）
真实世界充满了突发情况（线上紧急宕机、CTO 拍板带病上线等）。如果 `pt gate` 是一堵死墙，系统一定会被废弃或被伪造数据绕过。
*   必须允许在极其严格的条件下**强行冲破门禁**：
    `pt gate release --override --reason "Emergency Hotfix, manually verified by PM" --user "admin"`
*   Gate 被强行冲破，但这笔**技术债和责任审计日志**被永久记录在了系统里。既保证了敏捷，又实现了追责。

### 三、 总结：拍板后的终极业务流

一旦你决定把“强制闭环”作为基调，`project-tracker` 的各个模块将产生极强的化学反应，形成一套无可替代的**本地工程操作系统**：

1. **`pt req`（立法者）：** 产出不可篡改的工程契约（Contract）。
2. **`pt DAG/cpm`（执行者）：** 调度并完成契约规定的任务。
3. **`pt docs/review`（举证者）：** 收集契约已被履行的客观证据（Evidence）。
4. **`pt trace`（审计员）：** 核对契约与证据是否严丝合缝地匹配，出具审计报告。
5. **`pt gate`（审判长）：** 不看人情，只看审计报告，无情地下达 Go / No-Go 判决。

不要犹豫，走这条路。这正是 `pt` 从一众“玩具级”效率工具中脱颖而出、建立核心护城河的必经之路。
