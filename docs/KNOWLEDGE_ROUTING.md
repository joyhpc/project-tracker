# 项目经验沉淀与规则升级法则

## 目的

解决硬件项目中的一个高频混乱点：

- 项目过程里的经验、反思、踩坑记录，应该先放哪里
- 哪些内容应该只是项目知识，哪些应该升级成底层规则
- 如何避免 `project-tracker` 和 `sch-review` 职责混淆

本文给出默认法则和升级路径。

## 一句话法则

**默认先由 `pt` 接住项目现场索引，只有满足“跨项目复用 + 可定义检查条件 + 能形成规则/门禁”的条目，才升级到 `sch-review`。**

换句话说：

- **这是“这次项目为什么这么干”** -> 在 `pt` 里登记决策、PoC、review、风险或文档路径索引
- **这是“以后类似项目都应该这么查”** -> 放 `sch-review`

这里的“放 `pt`”不是把正式项目正文、测试原文、设计基线或发布结论写进 `project-tracker`。正式正文仍应写入 linked project repo；`pt` 只保存紧凑状态、摘要、路径和门禁元数据。

## 仓库职责边界

### `project-tracker` 的职责

`project-tracker` 是项目执行中枢，负责承接项目现场知识的索引和行动闭环。

适合放在 `pt` 的内容：

- 问题背景摘要和触发条件
- 当时的错误判断摘要
- 修复路径索引
- 决策理由摘要
- PoC 验证状态和证据路径
- 风险登记
- 下一阶段提醒
- 项目内复盘结论的路径挂接

这些信息的核心特征是：**强上下文、强时间性、依赖具体项目状态。**

正式需求、设计说明、验证记录、BOM、样机记录和发布结论属于 linked project repo，不属于 `project-tracker`。

### `sch-review` 的职责

`sch-review` 是审核引擎和规则知识库，负责把已经证明有效的经验抽象为可复用的检查能力。

适合放在 `sch-review` 的内容：

- 审核规则
- checklist 条目
- severity 分级
- YAML 配置
- 自动/半自动判定逻辑
- 可进入 gate 的审核依据
- 跨项目通用设计约束

这些信息的核心特征是：**弱项目上下文、强可复用性、可被检查或执行。**

## 默认工作流

### Step 1: 先在 `pt` 里接住现场经验

任何项目中的以下内容，默认先进入 `pt`：

- 复盘记录
- 决策登记
- PoC 跟踪
- 风险项
- review 结果

目标不是先做抽象，而是先把真实背景、约束、判断和结果记全。

### Step 2: 判断是否值得升级

只有当一条经验同时接近以下条件时，才考虑升级到 `sch-review`：

- 在多个项目中都可能出现
- 输入条件足够清晰
- 可以定义检查对象和判定标准
- 可以输出明确的提示、告警或阻断
- 不是一次性的项目偶发现象

推荐把下面 5 个问题当成升级门槛：

1. 这条经验会不会在别的板子上重复出现？
2. 能不能明确写出“检查什么”？
3. 能不能明确写出“什么算通过，什么算失败”？
4. 这条规则需要人工背景理解，还是工具也能执行？
5. 如果不升级，下次还会不会继续靠人记忆规避？

如果多数答案是“是”，就应该升级。

## 进入 `pt` 还是进入 `sch-review`

### 应该进入 `pt` 的情况

- 某次 bring-up 发现时序问题，但根因还没完全坐实
- 某器件替换方案被否决，原因涉及采购、交期、软件改动和封装联动
- 某问题需要做 PoC 才能确认，不适合直接写死成规则
- 某次错误只在当前项目架构、当前约束下成立

此时重点是保留完整上下文，而不是强行抽象。

### 应该升级到 `sch-review` 的情况

- 某类电源树错误在多个项目中反复出现
- 某类接口约束已经能稳定写成 checklist
- 某类拓扑/命名/约束冲突可以自动识别
- 某类问题已经足够稳定，适合纳入 `gate` 判定

此时重点是让经验变成可重复执行的工程能力。

## 升级判据

满足以下条件越多，越应该升级到 `sch-review`：

- **重复性**: 至少出现过 2 次，或明确具有跨项目通用性
- **可判定性**: 能定义输入、条件、阈值、结论
- **可分级性**: 能区分 P0/P1/P2 或 CRITICAL/WARNING/INFO
- **可测试性**: 能为规则补回归测试或数据集验证
- **可门禁性**: 结果可以影响 `pt gate`

如果一条经验只有“有启发”，但还没有清晰判定边界，就继续留在 `pt`。

## 推荐落点

### 在 `pt` 中的推荐落点

- `decision`：记录为什么拍板、为什么否决某方案
- `poc`：记录哪些假设还需要验证
- `review`：记录阶段性结论和风险摘要
- 项目复盘任务：记录硬件问题复盘、软件问题复盘

### 在 `sch-review` 中的推荐落点

- `config/*.yaml`：阈值、模式、severity、checklist 映射
- `rules/` 或规则引擎：判定逻辑和规则表达
- `docs/`：规则意图、使用边界、设计原则
- `tests/unit/` 与 `regression/`：保证规则稳定不回退

## 标准闭环

推荐使用下面这条闭环，而不是直接把复盘内容硬塞进规则库：

1. 在 `pt` 中记录项目现场经验
2. 通过决策、PoC、风险和复盘确认这条经验是否稳定成立
3. 将可复用部分抽象进 `sch-review`
4. 为新规则补测试或回归数据
5. 通过 `pt review-sync` / `pt gate` 把审核结果回流到项目执行

这条闭环的目标是：

- `pt` 保留上下文
- `sch-review` 保留可执行规则
- 两边职责清晰，但结果联通

## 反模式

### 反模式 1: 把所有复盘都直接写进 `sch-review`

问题：

- 会把规则库变成项目杂记
- 很多内容无法自动检查
- 后续维护时难以区分“通用规则”和“项目偶发现象”

### 反模式 2: 把所有经验都只留在 `pt`

问题：

- 经验只能被看到，不能被自动执行
- 同类错误会反复依赖人工记忆规避
- `gate` 和自动审核无法持续增强

## 推荐默认策略

如果团队没有时间争论放哪边，直接使用下面的默认策略：

1. 先在 `pt` 记录索引、摘要、状态和正式文档路径
2. 每次项目复盘后筛一轮“可升级条目”
3. 只有通过升级判据的条目才进入 `sch-review`
4. 进入 `sch-review` 的条目必须补规则表达和测试

## 示例

### 示例 1: 器件替换失败

结论：

- 先放 `pt`

原因：

- 涉及采购、交期、软件兼容、封装替换和验证成本
- 强依赖项目上下文
- 不一定能直接抽成普适规则

### 示例 2: I2C 上拉缺失在多个项目里重复出现

结论：

- 升级到 `sch-review`

原因：

- 具备跨项目重复性
- 检查对象明确
- 判定逻辑明确
- 可以给出告警等级

### 示例 3: bring-up 发现某电源域上电顺序风险

结论：

- 先放 `pt`
- 如果后续形成稳定时序约束模型，再升级到 `sch-review`

原因：

- 初期往往还处于假设和验证阶段
- 只有在规则边界清晰后才适合固化

## 最终结论

**`pt` 承接项目现场经验，`sch-review` 固化已证明有效的通用规则。**

默认动作只有一个：

**先由 `pt` 记录项目现场索引，再择优升级到 `sch-review`。**
