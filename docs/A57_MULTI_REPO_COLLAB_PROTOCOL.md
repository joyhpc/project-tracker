# A57 多 Repo 协作协议

Status: current protocol for A57-style hardware projects. It defines repository ownership boundaries, not project design content.

## 目的

本协议用于冻结 A57 类硬件项目在 `A57-docs`、`project-tracker`、`sch-review` 三个仓库之间的职责边界、读写方向和结论沉淀规则，避免出现多重真相、对象漂移和验证结论失真。

## 适用范围

- A57 下的 `CAMRX`、`DCURX` 等子项目
- 后续沿用同类治理方式的新硬件项目
- 人类工程师与 Coding Agent 的协同流程

## 三层架构

### 1. `A57-docs` = 项目真相层 / Data Plane

- 项目级需求、设计、接口、原理图说明、PCB 说明、样机台账、执行记录、验证记录、发布结论，统一以 `A57-docs` 为准。
- 任何会对外形成正式口径的内容，必须沉淀到 `A57-docs`。
- `CAMRX` 与 `DCURX` 可以共享方法，不共享正式设计文件。

### 2. `project-tracker` = 过程控制层 / Control Plane

- 负责任务编排、Issue/Discussion、方法模板、索引、同步、门禁和跨仓协作协议。
- 负责承接未闭环的问题、过程讨论、执行中的中间状态。
- 不负责保存某个项目的正式需求正文、正式设计正文或最终发布结论。

### 3. `sch-review` = 审核计算层 / Compute Plane

- 负责原理图解析、规则审核、结构化风险识别、证据提取和审核报告生成。
- 可以输出审核报告、风险报告、解析结果。
- 不得在本仓库中长期保存项目级正式需求、正式设计基线或发布结论。

## 绝对边界

### `A57-docs` 必须承接的内容

- 第一性原理需求
- 业务边界与系统原则
- 需求追溯矩阵
- 对象台账
- 版本锚点
- 当前有效结论页
- 样机、PCB、调试、验证、发布资料

### `project-tracker` 必须承接的内容

- 方法模板
- Issue / Discussion 交互
- 执行过程中的决策同步
- 当前待确认事项
- 跨仓动作的流程约束

### `sch-review` 必须承接的内容

- 解析器
- 审核规则
- 自动化检查
- 风险与证据提取
- 审核输出物

### 三个仓库都不得做的事

- 不得把同一条正式结论以不同版本长期维护在多个仓库中
- 不得把借用验证对象写成正式设计对象
- 不得把“据说跑通”“口头确认”当成正式闭环

## 正式对象与借用对象规则

### 正式对象

- 指当前子项目实际要交付、要发布、要形成正式设计基线的对象。
- 正式对象必须在 `A57-docs` 中有明确归属、对象台账、版本锚点和当前口径。

### 借用对象

- 指为验证节奏临时借用的板卡、固件、协议板、治具或其它项目对象。
- 借用对象可以服务于验证，但不能改变正式设计归属。
- 借用对象产生的结论必须明确写清：
  - 借用对象是谁
  - 来源 repo / 路径
  - 对应 revision / commit / 版本标识
  - 当前 owner
  - 借用目的是什么
  - 该结论适用于哪一侧
  - 哪些部分仍需回到正式对象上复验

若缺少上述最小元数据，借用对象只能视为临时参考，不得作为正式冻结、正式关闭或正式发布的依据。

### 禁止事项

- 禁止把 `CAMRX` 的临时验证对象写成 `DCURX` 的正式设计文件
- 禁止把 `DCURX` 的调试结论直接覆盖 `CAMRX` 的正式需求或设计口径
- 禁止在没有对象标识与版本锚点时发布“已跑通”结论

## 读写闭环

### 标准时序

1. 在 `project-tracker` 发起问题、任务或决策同步
2. 读取 `A57-docs` 当前真相层文档，确认正式对象、边界和版本锚点
3. 必要时调用 `sch-review` 生成审核结论、风险或证据
4. 在 `project-tracker` 完成过程讨论、试错与收敛
5. 将最终结论回写到 `A57-docs`
6. 只有当 `A57-docs` 的正式文档完成更新后，相关过程任务才允许进入真正闭环

### 判定原则

- `project-tracker` 里可以存在草稿结论
- `A57-docs` 里才允许存在正式结论
- `sch-review` 里可以存在审查发现
- 只有当审查发现被翻译并沉淀到项目文档后，才构成正式项目知识

## 证据锚点规则

任何声称“能力成立”“链路打通”“接口可用”“方案冻结”的结论，至少应绑定以下最小信息：

- 样机编号或实体对象标识
- 协议板 / 解码板 / 转接板对象
- 固件版本
- FPGA / RTL / 比特流版本
- 证据路径

如果当前阶段缺失其中一项，可以记录为“过程进展”，但不得记录为“正式结论”。

## 推荐目录约定

### `A57-docs`

- `01_需求阶段_Requirements/`
- `02_方案阶段_Architecture/`
- `03_详细设计阶段_Detailed_Design/`
- `04_PCB阶段_PCB/`
- `05_样机与调试阶段_Bringup_Debug/`
- `06_验证阶段_Verification/`
- `07_发布阶段_Release/`

### `project-tracker`

- `docs/` 放方法、协议、规则和交互同步文档
- `docs/issues/` 放供人类回复的同步议题

### `sch-review`

- `src/`、`slim/`、`config/`、`reports/` 等只承接审核与计算职责

## 执行红线

- 若发现某正式结论只存在于 `project-tracker`，应立即回写 `A57-docs`
- 若发现 `sch-review` 开始持久化项目真相层资料，应立即回退该设计
- 若发现借用对象与正式对象混淆，应先改正文档口径，再继续技术推进

## 与 Merge-to-Close 的关系

本协议定义多仓职责边界。

凡是涉及“能力成立、验证跑通、设计决策完成、正式冻结”的事项，还必须同时遵守 [`MERGE_TO_CLOSE_PROTOCOL.md`](./MERGE_TO_CLOSE_PROTOCOL.md)。
