# 依赖关系定义规范

Status: current DAG modeling rule. Validate implementation details against `tracker/engine.py` and `tracker/project_validation.py`.

## 核心原则
依赖关系 = "我的输入来自谁的输出"，不是"谁在我前面做"。

## 创建节点时的强制三问

### Q1: 这个任务的输入物是什么？
列出所有必需的输入（文档、硬件、固件、测试结果等）。
每个输入对应一个 depends。

### Q2: 这个任务的输出物是什么？
明确 deliverables。如果说不清输出什么，这个节点定义有问题。

### Q3: 谁会消费我的输出？
如果没有下游消费者，要么是项目终点，要么是孤立节点（check_integrity 会拦截）。

## 依赖灰度处理
现实中依赖不是布尔的。处理方式：
- **拆子任务**: 把粗粒度节点拆成多个细粒度子任务，每个子任务只依赖它真正需要的
- **不要用一个大节点代表一个复杂活动**: 调试、联调、测试都应该拆开
- **模板预定义**: 常见的分层依赖写成子任务模板（如 board_bringup）

## 常见错误模式

### 1. 顺序≠依赖
"A 在 B 后面做" 不等于 "A depends B"。
只有 "A 需要 B 的产出才能开始" 才是真依赖。

### 2. 遗漏隐性输入
硬件调试需要固件，但容易只写硬件依赖忘了固件。
联调需要软件+硬件+固件，容易漏掉其中一个。
→ 用分层子任务模板解决

### 3. 孤立终点
新增节点链没有接入下游流程。
→ check_integrity 自动拦截

### 4. 冗余依赖
A 同时依赖 B 和 C，但 C 已经依赖 B。
→ check_integrity 自动检测

### 5. 粗粒度节点掩盖并行机会
一个"板级调试"节点依赖所有上游，导致关键路径被拉长。
实际上调试的前几步不需要等所有上游。
→ 用 board_bringup 模板拆开
