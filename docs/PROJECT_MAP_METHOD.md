# 项目地图方法论与工具边界

> 生成日期: 2026-03-20
> 可信状态: 方法论与目标边界。当前已实现能力以 `tracker/project_map.py`、`docs/architecture.md` 为准；本文第 9-13 节包含目标契约和路线建议，不代表全部已经落地。
> 适用范围: `project-tracker`
> 文档性质: 方法论 / 架构决策文档
> 目的: 定义什么叫“项目地图”，为什么它不能退化成任务列表，以及 `pt` 与 `sch-review` 在项目地图能力上的职责边界

---

## 1. 为什么现在必须定义“项目地图”

`pt map` 当前实现已经能输出单项目地图、全局地图、stale/sync 风险摘要、阶段泳道、当前焦点、阻塞、关键路径和 close gate 摘要。它仍不能稳定回答下面这些更高层的问题：

1. 当前项目到底由哪些真实工程对象组成
2. 哪些对象已经可信，哪些对象只是前期验证载体
3. 当前阻断项目的到底是任务没做，还是对象没冻结
4. 当前结论到底绑定哪一个版本、哪一块板、哪一个样机实体
5. 当前最值得做的事，是继续推进任务，还是先冻结决策

这就是“任务地图”和“项目地图”的差别。

---

## 2. 什么叫项目地图

项目地图不是甘特图，不是 WBS，也不是单次审核报告。

项目地图的定义应该是：

> **把一个项目从根本目的一直压到可发布结论的关键对象、状态、卡点、决策和下一步动作，放在同一张可追溯视图中。**

换句话说，项目地图不是看“大家都做了什么”，而是看：

1. 项目为什么存在
2. 项目当前到底在交付什么
3. 当前交付对象是否已冻结
4. 当前哪里卡住了
5. 现在先做什么最值钱

---

## 3. 项目地图的第一性主链路

建议把项目地图固定建立在下面这条链上：

> **根本目的 -> 市场卖点/竞争目标 -> 系统原则 -> 业务场景 -> 子项目边界 -> 平台能力 -> 工程约束 -> 接口合同 -> 设计对象 -> 样机实体 -> 审核/验证/Bring-up -> 发布结论**

说明：

1. `根本目的`
   - 为什么要做这个项目，本质上为了拿市场、形成卖点、产生利润
2. `市场卖点/竞争目标`
   - 项目想靠什么特性形成竞争力
3. `系统原则`
   - 不侵入、可扩展、可复现、可演进等原则
4. `业务场景`
   - 项目服务哪些真实使用场景
5. `子项目边界`
   - 哪些是独立子项目，哪些只是临时借用验证对象
6. `平台能力`
   - 要覆盖哪些能力而不是只跑通一个点
7. `工程约束`
   - 速率、成本、功耗、供电边界、时序、EMC、可制造性
8. `接口合同`
   - 连接器、协议、控制平面、电源边界、状态信号
9. `设计对象`
   - 原理图、PCB、BOM、网表、固件、配置
10. `样机实体`
   - 实际可追溯的板卡和样机批次
11. `审核/验证/Bring-up`
   - 审核门禁、调试记录、压力结果、一致性结果
12. `发布结论`
   - Go / Conditional / No-Go

项目地图的价值，恰恰在于把这 12 层压成一个统一快照。

---

## 4. 一个合格项目地图最少要有的 6 个视图

### 4.1 产品对象拓扑图

回答：

1. 项目由哪些主板、子板、桥接板、固件和样机对象组成
2. 哪些对象是正式对象，哪些只是前期验证对象

### 4.2 版本对象状态表

回答：

1. 每个对象当前是不是有唯一版本
2. 设计/BOM/PCB/固件/样机是否绑定

### 4.3 阻断图

回答：

1. 哪些是 `P0/P1/P2`
2. 每个阻断影响的是一个板、一个专项，还是整个子项目

### 4.4 决策冻结图

回答：

1. 哪些事情已经拍板
2. 哪些地方仍然在漂
3. 哪些未冻结决策会放大返工半径

### 4.5 执行路径图

回答：

1. 当前关键路径是什么
2. 下一步应该先锁对象、锁风险，还是继续做实现

### 4.6 发布口径图

回答：

1. 当前是 `Go / Conditional / No-Go / Not Ready`
2. 当前结论是否允许对外宣称

## 5. `pt` 为什么应该拥有“项目级地图”

结论先写清楚：

> **`pt` 应该负责项目级地图，不能把这层责任丢给 `sch-review`。**

原因：

1. `pt` 天然掌握项目、阶段、关键路径、依赖和下一步执行链
2. 项目地图需要同时接入需求、决策、对象状态、审核信号和执行状态
3. `sch-review` 擅长的是板级事实，不擅长跨子项目整合
4. 项目地图是“项目中枢能力”，不是“单板审核报告扩展页”

因此，`pt` 的正确角色是：

1. 聚合项目级输入
2. 构建统一快照
3. 输出给终端、HTML、GitHub 文档和交接使用

---

## 6. `sch-review` 为什么也值得做“地图能力”

这件事也要写清楚：

> **`sch-review` 也值得做地图，但只应该做板级地图，不应该越界做项目级地图。**

`sch-review` 最适合输出的是：

1. 单板对象拓扑
2. 审核门禁状态
3. BOM/网表/接口合同一致性
4. Bring-up 风险
5. 板级版本锚点和未闭合问题

也就是说，`sch-review` 的“地图”本质上应该是：

> **板级设计包真相图 / 板级状态快照**

而不是整项目的主地图。

---

## 7. 三者的正确分工

项目地图能力建议固定成下面这套分工：

### 7.1 文档仓库

例如 `A57-docs`。

作用：

1. 承接人类审阅
2. 固化结论页、版本锚点、需求矩阵、专项页
3. 形成 GitHub 可讨论入口

### 7.2 `sch-review`

作用：

1. 生成板级真实状态
2. 输出审核结论和板级门禁
3. 输出面向项目地图消费的结构化快照

### 7.3 `project-tracker`

作用：

1. 聚合任务态 + 决策态 + 对象态 + 审核态
2. 形成项目级地图
3. 给出关键路径、当前焦点和下一步动作

简化成一句话：

> **文档仓库负责“让人审”，`sch-review` 负责“让板说真话”，`pt` 负责“让项目说真话”。**

---

## 8. `pt` 应该以什么为中心调用

推荐明确拍板：

> **`pt` 必须以开发中的项目为中心，而不是以 `pt` 自己的仓库目录为中心。**

这意味着：

1. `pt` 的运行位置可以在 `project-tracker` 仓库中
2. 但它处理的核心对象必须是某个被绑定的项目
3. 这个项目要显式绑定：
   - 项目文档仓库
   - 主设计仓库
   - 板级审核产物路径
   - 当前子项目对象

因此未来的 `pt map`，应该优先支持下面几类调用：

```bash
pt map --project A57
pt map --project A57 --subproject DCURX
pt map --project A57 --view project
pt map --project A57 --view subproject
```

而不是依赖“当前人在 `pt` 哪个目录里运行”来推断语义。

---

## 9. 面向实现的最小数据契约

建议 `pt` 消费下面 4 类输入：

### 9.1 需求与决策输入

来自项目文档仓库：

1. 根本目的
2. 子项目边界
3. 应用目标矩阵
4. 当前有效结论
5. 版本锚点

### 9.2 任务与关键路径输入

来自 `projects/*.yaml`：

1. 节点状态
2. 依赖关系
3. 关键路径
4. 当前焦点

### 9.3 板级状态输入

来自 `sch-review` 导出：

1. `board_id`
2. `design_version`
3. `bom_version`
4. `netlist_version`
5. `pcb_version`
6. `firmware_version`
7. `sample_version`
8. `gate_status`
9. `open_blockers`
10. `confidence`

### 9.4 证据输入

来自执行记录和验证记录：

1. Bring-up 记录
2. 压力验证记录
3. 换板记录
4. 异常归因记录
5. 一致性记录

## 10. 推荐的产品化路线

### A 方案

继续把 `pt map` 只当任务地图用。

特点：

1. 实现最轻
2. 但对硬件项目的真实价值有限

### B 方案

把 `pt map` 升级为“项目级地图”，并消费 `sch-review` 的板级状态快照。

特点：

1. 最符合硬件项目管理实际
2. 能把任务、对象、决策、审核和发布统一到一起

### C 方案

让 `sch-review` 和 `pt` 各自独立做完整项目地图。

特点：

1. 表面上都能出图
2. 实际上会出现两套真相源

---

## 11. 当前建议

> **选 `B`。**

具体落地方式：

1. `sch-review` 新增板级状态导出能力
2. `pt` 新增项目级地图快照构建能力
3. 文档仓库继续承接人类审阅版项目地图

---

## 12. 如果选错会怎样

如果继续停留在“任务地图”层，或者让两个工具各自做一套项目真相，后果通常是：

1. 大家都觉得信息很多，但没人能回答“当前项目到底卡在哪”
2. 审核结论和项目结论分裂
3. 任务在推进，但关键对象仍未冻结
4. 版本和样机不绑定，结论不可复现

---

## 13. 下一步最值得做的实现

1. 在 `sch-review` 定义板级状态导出契约
2. 在 `pt` 为 `project / subproject / board` 三层视图预留数据模型
3. 用 `A57 / DCURX` 作为第一批真实样例，把“项目地图”从概念变成可运行能力

---

## 14. 当前统一口径

> **项目地图不是“更好看的任务列表”，而是把项目从第一性目标一直压到发布结论的统一真相图；`pt` 应该拥有项目级地图，`sch-review` 应该提供板级真相快照，文档仓库负责承接人类审阅与冻结口径。**
