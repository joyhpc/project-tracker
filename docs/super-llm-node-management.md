# 超级LLM问题：Project Tracker 节点动态管理系统设计

## 背景

Project Tracker (pt) 是一个基于 DAG（有向无环图）的硬件项目管理 CLI 工具。当前架构：

- **数据模型**：扁平节点列表，每个节点有 `id, name, phase, status, depends, days, owner` 等字段
- **依赖关系**：邻接表（`depends` 写在节点里），支持跨阶段依赖
- **引擎**：CPM 关键路径分析（前向/反向推导 + Slack）、Kahn 拓扑排序 + 环检测
- **完整性检查**：6 类自动检测（孤立终点、悬空依赖、里程碑缺上游等）
- **规模**：5 个项目，最大 116 节点（A57），代码 ~3200 行 / 19 模块 / 30 命令

### 当前痛点

项目执行过程中，频繁需要**动态增删改节点并重新接入 DAG**：

1. **中途加任务**：验证方案变更（如 JW7221→LM5060）、新增验证项（CPHY桥接）、采购任务（陪测单元）
2. **批量导入**：用户口述 7 项待办，需要逐个创建节点、分配阶段、接依赖、检查完整性
3. **方案替换**：某个验证方案被否决，需要替换为新方案，所有下游依赖自动重接
4. **节点拆分**：一个粗粒度任务需要拆成多个子任务，依赖关系要正确继承

当前做法：**每次都写临时 Python 脚本**，手动操作节点列表和依赖数组。容易出错（忘记接依赖→孤立终点），不可复用，不可审计。

### 现有 API

```python
# 已有的节点操作（都是针对子任务的，不支持一等节点的增删）
add_subtask(project_id, parent_id, subtask_id, name, **kwargs)
done_subtask(project_id, full_id, note)
block_subtask(project_id, full_id, reason)

# 已有的完整性检查
check_integrity(project, cpm) -> list[dict]  # 6类检测

# 没有的：
# - 添加一等节点
# - 删除/归档节点
# - 批量导入节点
# - 依赖重接/替换
# - 节点移动（跨阶段）
```

### 数据模型示例

```yaml
# 一个典型节点
- id: cphy_bridge_verify
  name: CAMRX CPHY桥接方案验证(60K)
  phase: DETAIL
  status: pending
  depends: []
  days: 5
  owner: 硬件工程师

# 带子任务的节点（子任务是扁平化的一等节点，用 . 分隔层级）
- id: cphy_bridge_verify.io_expand
  name: IO扩展功能验证
  phase: DETAIL
  status: pending
  depends: [cphy_bridge_verify]
  days: 2
  parent: cphy_bridge_verify  # 可选，标记父子关系
```

## 核心问题

### Q1: `pt add` — 节点添加的最优交互设计

**场景**：用户在项目执行中需要动态添加 1~N 个节点，并正确接入现有 DAG。

**需要回答**：

1. **单节点添加的 CLI 接口设计**：参数怎么设计最符合工程师的心智模型？
   - 必须参数 vs 可选参数的划分
   - `--depends`（上游）和 `--feeds`/`--before`（下游自动接入）是否都需要？
   - 阶段（phase）应该显式指定还是从依赖关系自动推断？
   - ID 生成策略：手动指定 vs 从名称自动生成 vs 混合

2. **批量添加的最优方式**：
   - 用户口述"7项待办"时，最高效的输入方式是什么？
   - YAML 文件导入 vs 交互式逐条添加 vs 自然语言解析？
   - 批量添加时的依赖关系如何表达？（批内互相依赖 + 与现有节点的依赖）

3. **自动接入 DAG 的策略**：
   - 添加节点后，如何自动检测"应该接入哪个下游节点"？
   - 是否需要"插入点"概念（在 A 和 B 之间插入 C，自动重接 A→C→B）？
   - 添加后自动跑 `check_integrity` 并报错/建议？

4. **防错机制**：
   - 添加后发现接错了怎么办？需要 undo 吗？
   - 如何防止重复 ID？
   - 如何处理"添加了但忘记接依赖"的情况？

### Q2: `pt remove` / `pt archive` — 节点删除与归档

**场景**：验证方案被否决（如 JW7221 方案作废），需要从 DAG 中移除相关节点。

**需要回答**：

1. **删除 vs 归档**：硬删除还是标记为 archived？对历史追溯的影响？
2. **级联处理**：删除一个节点时，它的子任务怎么办？依赖它的下游节点怎么办？
   - 选项 A：级联删除所有子节点
   - 选项 B：子节点提升为独立节点
   - 选项 C：拒绝删除有下游依赖的节点，要求先重接
3. **依赖修复**：删除后，上下游的依赖链断裂怎么自动修复？
4. **与 git 的协同**：删除/归档操作是否需要自动 commit？

### Q3: `pt rewire` — 依赖关系批量重接

**场景**：方案变更时，需要将一组节点的依赖从旧方案切换到新方案。

**例子**：
- 原来：`camrx_sch_base` 依赖 `jw7221_verify` → 现在改为依赖 `lm5060_verify`
- 原来：`hw_sw_integration` 不依赖陪测单元 → 现在需要加入 `companion_test_unit.serial_board`

**需要回答**：

1. **重接的粒度**：
   - 单条依赖替换：`pt rewire camrx_sch_base --replace jw7221_verify lm5060_verify`
   - 批量替换：所有依赖 X 的节点，自动改为依赖 Y
   - 子图替换：把一组旧节点替换为一组新节点，自动重接所有上下游

2. **安全性**：
   - 重接后是否可能引入环？如何检测和阻止？
   - 重接后关键路径可能变化，是否需要 diff 展示？
   - 是否需要 dry-run 模式（先展示变更，确认后执行）？

3. **与 `pt add` 的协同**：
   - 添加新节点时能否同时指定"替换哪个旧节点的位置"？
   - 一条命令完成"添加新方案 + 归档旧方案 + 重接依赖"？

### Q4: 节点 ID 命名规范与层级表达

**当前状态**：ID 用 `.` 分隔表达层级（如 `fpga_dev.mipi_3g5_verify.adapter_design`），但这是约定而非强制。

**需要回答**：

1. **ID 自动生成策略**：
   - 从中文名称生成英文 ID 的最佳方式？（拼音？关键词翻译？缩写？）
   - 子任务 ID 是否强制带父节点前缀？
   - ID 长度限制？可读性 vs 唯一性的平衡？

2. **层级深度**：
   - 当前最深 3 层（`fpga_dev.mipi_3g5_verify.adapter_design`），是否需要限制？
   - 层级过深时 CLI 显示如何处理？

### Q5: 整体架构 — 这些能力应该如何组织？

**需要回答**：

1. **模块划分**：
   - 新增一个 `tracker/node_ops.py` 模块？还是扩展现有 `core.py`？
   - `core.py` 已经 931 行，继续膨胀还是拆分？

2. **事务性**：
   - 批量操作（添加 11 个节点 + 接 5 条依赖）是否需要原子性？
   - 失败时回滚到操作前状态？

3. **审计日志**：
   - 每次节点变更是否需要记录操作日志？（谁在什么时候添加/删除/重接了什么）
   - 日志格式和存储位置？

4. **与现有命令的关系**：
   - `pt sub`（子任务）和 `pt add`（一等节点）的边界在哪？
   - 是否需要统一为一个命令？
