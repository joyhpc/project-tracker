## 版本演进

| 版本 | 核心方法 | 问题 |
|------|---------|------|
| v1-v2 | 实体提取 + 信号检测 | 648 行代码，过度工程化 |

## v4 架构设计

### 设计原则

1. **不用信号词，不用 LLM API** — 纯数学检索，确定性输出
2. **不破坏结构** — 表格、对比矩阵原样保留，不提取零散句子
3. **问什么给什么** — 根据问题自动检索最相关的知识块，不是全部堆进去
4. **零字典维护** — IDF 自动给专业术语高权重，换项目不改代码

### 核心模块：knowledge.py

#### 1. Markdown AST 切块 (`parse_markdown`)

```
输入: 自由格式 Markdown 文档
输出: KnowledgeChunk[] — 按标题层级切分的知识块

# 硬件架构          ← 切分点
## 核心模块选型      ← 切分点，path = ["硬件架构", "核心模块选型"]
| 模块 | 方案 |     ← 表格原样保留在 chunk.content 中
| 主控 | ESP32 |
## 声振解耦         ← 新切分点
频段分离策略：...    ← 保留在 chunk.content 中
```

**为什么按标题切？**
- 用户写 Markdown 时自然会用标题分段，这是零成本的语义边界
- 每个标题下的内容是一个完整的知识单元（选型表、BOM 清单、测试方案）
- 保留了 `path` 层级信息，LLM 能理解知识的来源和上下文

**Fallback**：如果文档没有标题，按段落（双空行）切分

#### 2. 混合分词 (`tokenize`)

```python
tokenize("VCM音圈换能器20-50Hz低频")
→ ["vcm", "20-50hz", "音", "圈", "换", "能", "器", "20", "-", "50", "hz",
   "音圈", "圈换", "换能", "能器"]  # 英文连字 + 中文单字 + Bigram
```

**为什么用 Bigram？**
- 不依赖 jieba 等第三方分词库（零依赖）
- Bigram 对专业术语覆盖率足够："降维"、"打击"、"声场"、"偶极"都能命中
- 英文连字完美捕获硬件术语：stm32、type-c、0.1uf、i2c

#### 3. BM25 检索引擎

```
BM25 公式：
score(q, d) = Σ IDF(qi) × (tf(qi, d) × (k1 + 1)) / (tf(qi, d) + k1 × (1 - b + b × |d| / avgdl))

其中：
- IDF(qi) = log(1 + (N - df(qi) + 0.5) / (df(qi) + 0.5))
- tf(qi, d) = 词 qi 在文档 d 中的出现次数
- |d| = 文档 d 的长度
- avgdl = 所有文档的平均长度
- k1 = 1.5, b = 0.75（标准参数）
```

**为什么用 BM25？**
- ElasticSearch 的底层算法，经过 30 年工业验证
- IDF 机制天然给专业术语高权重（"VCM" 比 "的" 重要 100 倍）
- 纯数学，确定性输出，零依赖
- 毫秒级性能（几十个文档 < 1ms）

#### 4. 查询扩展 (`retrieve_context`)

```
用户问题: "VCM 低频传导可行性"
     ↓ 扩展
联合查询: "可行性分析 [当前任务note] VCM 低频传导可行性 市场调研 概念设计"
                                                          ↑ 依赖链任务名
```

**为什么要查询扩展？**
- 用户问题通常很短，直接检索召回率低
- 加入当前任务名和 note，让检索偏向当前阶段的相关知识
- 加入依赖链任务名，因为上游任务的知识天然最相关

### 核心模块：prompt.py

#### 问题类型 → 角色 + 聚焦上下文 + 任务指令

| 类型 | 角色 | 聚焦上下文 | 任务指令 |
|------|------|-----------|---------|
| decision | 产品战略顾问 | 待决策选项矩阵 | 推荐组合 + 核心逻辑 + 风险对策 |
| solution | 硬件架构师 | 当前任务 + 交付物 | 选型对比表 + BOM + 风险点 |
| risk | 红队评估专家 | 关键路径 + 下游影响 | Top 3 风险 + 概率 + 应对 |
| strategy | 战略顾问 | （BM25 已包含） | 定位 + 陷阱 + 路径 |
| general | 硬件产品专家 | （BM25 已包含） | 结论先行 + 可执行 |

**为什么保留问题类型检测？**
- BM25 解决了"给什么上下文"的问题
- 但"用什么角色"和"要求什么输出格式"仍然需要类型区分
- 关键词匹配足够轻量且准确，不需要 LLM

### Prompt 输出结构

```markdown
**角色**：你是一位...                    ← 一句话角色设定

**项目背景**：
我们正在开发一款「智能助眠枕头」。
- **核心定义**：...                      ← 引用块规则提取
- **相关历史结论**：                      ← BM25 Top-5

<reference source="[概念设计] 核心模块选型">
| 模块 | 方案 | 淘汰方案 |              ← 表格原样保留
| 主控 | ESP32+DSP | 纯MCU ❌ |
</reference>

<reference source="[市场调研] 低频体感盲测">
- 致命指标：酥麻放松 vs 心烦？          ← 结构化数据完整
</reference>

- **当前阶段**：概念阶段（2/24，39天）

**当前任务**：可行性分析（关键路径）      ← 聚焦上下文（按类型）

**你的任务**：                           ← 用户问题
VCM 低频传导可行性...

请给出具体方案，包含：                   ← 输出要求模板（按类型）
1. 技术选型对比表
2. BOM 成本预估
3. 关键风险点
```

### v3 → v4 对比

| 维度 | v3（信号词） | v4（BM25） |
|------|------------|-----------|
| 知识提取 | 信号词匹配零散句子 | AST 按标题切块，保留完整结构 |
| 上下文选择 | 全部堆进去（最多 8 条） | BM25 Top-5 相关块 |
| 结构化数据 | 丢失（表格被打散） | 原样穿透（XML 封箱） |
| 可扩展性 | 需维护信号词列表 | IDF 自动适应，零维护 |
| 代码量 | prompt.py 328 行 | knowledge.py 189 行 + prompt.py 310 行 |

### 实际效果验证

同一个项目，不同问题检索到完全不同的上下文：

```
问"VCM可行性"  → 声振解耦架构 + 选型表 + 低频盲测方案
问"偶极子声场"  → 选型表 + 声场架构 + 伴侣干扰摸底
问"BOM成本"    → BOM表格(排第一) + 选型 + PoC物料清单
问"PoC方案"    → PoC物料清单 + 测试项 + Go/No-Go标准
```
