   ├─ 功能: Kahn拓扑排序 + CPM关键路径 + Slack计算 + 智能工时估算
   ├─ 依赖入口: core.py → engine.py → {prompt.py, risk.py, project_map.py}
   ├─ 数据质量: 直接影响所有后续分析的准确性
   └─ 测试: ⚠️ 缺CPM精度单测 (建议补充)

2. ⭐⭐⭐⭐ BM25知识检索 + LLM Prompt生成 (knowledge.py 215行 + prompt.py 506行)
   ├─ 功能: Markdown切块 + 硬件术语增强分词 + BM25数学检索 + 角色聚焦
   ├─ 创新点: 无需LLM API的本地检索 + 实时DAG数据融合
   ├─ 用途: pt prompt --deep 一键生成高质量LLM提示词
   └─ 测试: ❌ 完全无单元测试 (高优先级补充)

3. ⭐⭐⭐⭐ 投板门禁系统 (close_gate.py 135行 + gate_cmd.py 200行)
   ├─ 功能: sch-review P0/P1/P2自动映射 + 门禁条件聚合 + 阻断清单
   ├─ 集成: sch-review + opendatasheet
   ├─ 用途: pt gate <node> 投板决策有据可查
   └─ 测试: ✅ test_close_gate.py (8.2KB)

4. ⭐⭐⭐⭐ 项目状态机 + 持久化 (core.py 1865行 + project_mutation.py 275行)
   ├─ 功能: YAML版本迁移 + Schema演进 + 状态转移规则 + 事务性保存
   ├─ 复杂度: 🔴 高 (涉及数据兼容性与可靠性)
   └─ 测试: ✅ test_project_mutation.py (4.9KB)

5. ⭐⭐⭐ 需求体系平台化 (requirements.py, 778行)
   ├─ 功能: 追溯矩阵模板 + 自动索引 + 完整性校验 + 多项目汇总
   ├─ 用途: pt req init/trace/check 硬件需求全链路
   └─ 测试: ✅ test_requirements.py (8.7KB)

【主要技术负债】
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

🔴 问题1: core.py 上帝类 (1865行, 总代码24%)
   ├─ 职责: YAML I/O + 数据迁移 + 40+个Internal API + 命令代理
   ├─ 影响: 修改需全量测试 | 难以理解数据流 | 新功能堆积
   ├─ 方案:
   │  ├─ core_io.py (YAML I/O, ~200行)
   │  ├─ core_migration.py (版本迁移, ~300行)
   │  ├─ core_api.py (Internal API, ~800行)
   │  └─ core_facade.py (公开接口, ~200行)
   └─ 预期: 单文件<500行 | 可独立测试 | 降低改动影响范围

🟡 问题2: 命令层冗余 (27个文件, 部分仅薄包装)
   ├─ 示例: conflict_cmd(8) → guide_cmd(37) → risk_cmd(33) → notify_cmd(30)
   ├─ 影响: 文件过多导航混乱 | 重复的"获取项目"逻辑
   ├─ 方案:
   │  ├─ 合并薄命令到 analysis.py
   │  ├─ 保留复杂命令 (review_cmd/node_cmd/tasks.py)
   │  └─ 建立 command_base.py 统一基类
   └─ 预期: -8~10个文件 | 新命令开发时间-40%

🟡 问题3: 循环依赖隐患
   ├─ engine.py ←→ project_map.py (都用build_graph)
   ├─ risk.py ←→ prompt.py (都用engine + cpm)
   └─ 方案: 提取 graph_utils.py 作为共享库

🟡 问题4: 测试覆盖率低 (~40%)
   ├─ 缺失: guide.py | conflict.py | fuzzy.py | knowledge.py
   ├─ 高优先级补充:
   │  ├─ knowledge.py: 分词 + BM25单测
   │  ├─ engine.py: CPM精度验证
   │  └─ fuzzy.py: 意图识别用例
   └─ 预期: 覆盖率 > 70%
